## 问题 1 [P0] — Playtest 反馈的数据采集路径

**原始问题**: 如何记录绕过 Django 的 LightRAG 反馈？

**用户回答**: A. 前端上报 — 前端收到 LightRAG 响应后，额外调用一个 Django API 保存反馈记录

**澄清结论**: Playtest 反馈记录采用「前端上报」方案——前端在收到 LightRAG 响应后，调用新增的 Django 反馈记录 API 保存，不改动 NGINX 代理链路。

**影响**: 需要新增 Django 保存 API + 修改前端 playtest 反馈组件增加上报逻辑。

---

## 问题 2 [P0] — 版本记录的触发时机

**原始问题**: "修改提交"的触发时机？是 Django 保存接口还是更细粒度？

**用户回答**: C. 生成 AI 反馈时 — 以点击"Generate Feedback"的时刻快照当前答案

**澄清结论**: 答案版本记录在每次点击"Generate Feedback"时创建（快照当前答案文本），版本与 AI 反馈一一对应；不生成反馈则不产生新版本。

**影响**: 版本粒度 = 每次 AI 反馈生成；答案版本与 AI 反馈记录通过同一请求事务写入；前端需在生成反馈成功后上报。

## 问题 3 [P1] — 历史数据回填

**原始问题**: 已有 `FeedbackInitialResponse` 历史记录是否回填为第一个版本？

**用户回答**: A. 需要回填

**澄清结论**: 将 `FeedbackInitialResponse` 中已存在的历史记录回填为每个学生/问题组合的 version 1，保证科研时间线完整。

**影响**: 需要编写数据迁移脚本；回填的 version 1 无关联 AI 反馈记录。
